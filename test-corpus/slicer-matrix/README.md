# Slicer matrix corpus

Written by an AI agent (Claude). Our own test models (generated by `scripts/models.py`, MIT like the rest of this repo), sliced on 2026-10-10 by real installed slicers, and the values each slicer stated about its own output. Because we made the models, the sliced files can live in the repo; third-party samples stay out (see docs/reference-data.md).

`manifest.json` lists every file with `stated_weight_g` / `stated_time_s` (read from the file by `truth.py`, independently of our parser), `stated_filament_g` (grams per filament) for multi-material files, `stated_length_mm` / `stated_volume_mm3` for Cura, `expect_slicer`, and whether it should parse or be rejected. Three files over 3 MB are listed but not committed (`committed: false`). `src/corpus.test.ts` checks all committed files in CI.

To regenerate: install the slicers on Windows, run `models.py <dir>/models`, flatten presets into `<dir>/profiles` (see the commands at the top of each flatten script), then `SHTEST=... SHTEST_WIN=... scripts/run_matrix.sh` (add `CASES='^(P1|C)'` to re-run only some cases). Then run the parser harness over `<dir>/cases` and `scripts/truth.py <dir>/cases results.json` to compare.

CLI notes, learned the hard way:
- Bambu Studio and OrcaSlicer's CLIs need the system printer preset file plus a flattened filament preset; flattened printer or process presets are refused as "not compatible". But Bambu Studio doesn't resolve `inherits` in a passed file, so with the plain system file the B01-B07 cases ran with fallback values for keys the P1S file inherits (for example the generic `machine_start_gcode` and `single_extruder_multi_material = 0`). Their stated numbers are still the slicer's own. Multi-filament needs the real values, so B08/B09 use `flatten.py ... system`: inheritance resolved, but the system name kept, so the CLI accepts it.
- Multi-filament on Bambu/Orca: every filament preset needs a `filament_colour`, or the CLI crashes (exit 5, no message) as soon as the second filament is used. Orca also checks that `filament_is_support` has one value per filament. Hand-written project 3MFs (with `model_settings.config`) also crashed Bambu Studio; generic 3MFs load, but their per-object extruder is ignored.
- CuraEngine alone only reads each setting's `default_value`. The Cura app evaluates the Python `value` formulas and its quality/material/variant profiles first. `cura_settings.py` resolves the definitions and formulas (not the profiles) into flat JSON files for `-j`, and `cura_header.py` swaps in the real header the engine logs at the end (the file gets `;TIME:6666` / `;Filament used: 0m` placeholders) and strips the input path from `;MESH:` lines. So these files have the app's header format, but the numbers differ from what the Cura app would produce for the same model and printer (different profiles, no `;SETTING_3` footer). App exports (an Ender-3 `.gcode`, an S5 `.ufp`) would still be worth adding.
